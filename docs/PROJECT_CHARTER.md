# HobbyLib 项目章程

状态：目标与长期约束，2026-10-26。现状证据见 [审查报告](REVIEW-2026-10-26.md)，实施入口见 [Codex Prompt](CODEX_IMPLEMENTATION_PROMPT.md)。本文件不表示下述能力已经全部实现。

## 要解决的问题

HobbyLib 是个人兴趣商品库与中古收藏品发现助手，覆盖书籍、漫画、手办、玩具和周边。Collector Radar（收藏雷达）是当前网站及实现的来源；HobbyLib 是长期项目名称。沿用现有 Sites 项目身份，名称演进不等于重建网站或迁移数据库。

用户需要把大量杂乱的店铺记录对应到可靠的发行商品，整理系列、版本、特典及组件，随后让每天新增的挂牌进入同一套判断流程，支持缺件提醒、比价和购买建议。当前 Fate/TYPE-MOON 数据用于试点，不应成为只能支持 Fate 的架构限制；Chiyoko 是历史兴趣示例，具体角色身份和关注范围须由用户资料确认。

最终体验：用户看到一个稳定的商品档案，能追溯日文原名、版本、来源证据、所属系列、拥有状态及不同店铺报价；能看懂“为什么匹配、为什么推荐、哪里仍未知”。疑难项集中处理，已确认事实可复用，换工具或助手后可从文档与断点继续。

## 三种关系必须分开

1. 目录归类：作品/IP → 媒介或商品类别 → 产品线/发行系列 → 版本或款式。它帮助浏览，同一目录不代表同一商品。
2. 商品身份：实际发行、可独立辨识的版本/款式是匹配单位。原版小说、文库版、漫画、不同卷、不同平台、不同卡面各有身份。
3. 物理组成：原厂套装包含组件，本体关联独立特典，卖家拼套包含此次实际出售的成员。组成关系不把成员合并，也不自动继承拥有状态。

发行系列档案不是卖家出售的一件商品；目录父级没有报价不应被判作缺货。原厂完整目录、推测成员和实际挂牌内容应明确区分。

## 架构方向

继续使用现有 Item、嵌入式 Offer、Relation 与用户隔离存储；先给现有规则增加可解释决策、证据及复查产物，再根据实测瓶颈决定是否新增表或拆模块。不得仅为术语漂亮引入 Work/Product/Edition 多套重复实体。

目标数据流：来源页面/结构化数据 → 保留原始观测与来源键 → 标准化与局部事实抽取 → 索引召回候选 → 硬冲突检查 → 匹配决定或待复查 → 更新挂牌与有来源的商品字段 → 层级/关系建议 → 偏好评分、报价可比性与通知事件。

历史清理与增量采集共用事实解析、身份规则和决策格式。历史任务只生成可审阅计划；增量任务先以影子模式记录新旧判断差异，再逐来源启用经验证的自动关联。自动关联挂牌不等于授权合并两个商品档案。

批量处理采用有界投影、候选索引、按系列共享来源事实、缓存与断点。AI 只处理规则无法确认的少量项目；AI 产出是带证据的建议，不能覆盖硬冲突或自行声称完成核实。额外模型 API 尚未接入，不在本次文档工作中接入付费服务。

## 成功标准

- 任何自动匹配均可复现，记录规则版本、证据、冲突及选择理由；歧义和资料不足可安全保留。
- 原始复查编号、个人备注、人工字段、拥有数量、优先度、历史报价与归并存档可追溯且可恢复。
- 系列缺款只基于已核实的成员范围，区分“未收录”“明确未拥有”“拥有状态未知”。
- 在留出标注集测量自动关联精确率、召回率、复查率、硬冲突误关联数；按来源和品类分别报告，并给出样本数与不确定性。没有足够样本时保持建议模式，不捏造达标结果。
- 持续处理的耗时、内存、来源请求数、AI 成本及缓存命中率有实测记录；不能把传输字节减少当作 token 或人工成本同比减少。
- 通知具有事件去重和补货语义，旧库存、竞拍价、整套价、成色与费用未知均明确标识。

## 范围与发布

近期优先级：匹配安全与评测 → 历史批量计划 → 层级和标签 → 增量影子验证 → 通知及价格推荐。外部推送、常驻云监控、复杂向量库、自动购买不是当前已交付能力。

每次变更更新对应事实文档、相关回归与验证记录；业务契约变更写明理由、数据兼容与回滚。GitHub PR、Sites 发布、生产数据库更新分别验证；文档 PR 不触发生产数据修订。仓库持续保持私有。
